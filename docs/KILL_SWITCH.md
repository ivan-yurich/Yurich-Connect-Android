# Kill switch Android

Защита использует системный firewall Android, а не таймер переподключения.
В настройках Android → VPN → Yurich Connect пользователь включает **Постоянная
VPN** и **Блокировать соединения без VPN**. Приложение не меняет эти переключатели
самостоятельно и не требует root/Device Owner/WRITE_SECURE_SETTINGS.

На проверенном HONOR/Android 16 параметры открываются **долгим нажатием** на
Yurich Connect → **Изменить**. Название lockdown-переключателя на этой прошивке —
**Разрешить соединение только через VPN**, а не «Блокировать соединения без VPN».

## Состояния и границы

- Краткий приватный bind-only сервис запрашивает `VpnService.isAlwaysOn/isLockdownEnabled`.
  Runtime отвечает через зарегистрированный `NOT_EXPORTED` ordered broadcast, как
  существующая проверка готовности. Запрос не создаёт и не перезапускает VPN.
  Недоступный ответ — отдельное `runtimeKnown=false`, а не «TUN нестрогий».
- Полный зелёный статус требует также действующего строгого TUN. После изменения
  системных настроек приложение повторно проверяет состояние и применяет маршруты.
  Параллельные проверки объединяются только на время живого запроса; сохранённой
  галочки «включено» нет. В foreground состояние обновляется каждые 20 секунд.
  Неопределённый runtime не вызывает применения маршрутов или переподключения.
- Запрос строгих маршрутов хранится отдельно в device-protected atomic-файле под
  межпроцессной блокировкой. Это только намерение, не доказательство firewall.
  Публичные флаги Android могут быть false до `establish()`/во время recycle TUN;
  такой ответ не снимает строгий режим. Перед выходом в настройки и закрытием TUN
  намерение сохраняется, а положительный нативный флаг защёлкивает его при старте.
  Повреждение/ошибка чтения хранилища не разрешает прямой fallback.
- Автопроверка требует Android 10/API 29+. На API 24–28 строгие маршруты можно
  запросить вручную, но системная блокировка не подтверждается этим приложением.
- При системном Always-on намерением управляет Android, не кэш started/manual
  в другом процессе. Даже при устаревшем кэше статус требует реального native
  ответа нужного fingerprint; Always-on сам по себе не выдаётся за готовность.
- При смерти `:vpn`, закрытии TUN, reload и смене сети блокировку держит ОС.
  Неудачное восстановление означает отсутствие интернета, не прямой fallback.
- Strict policy включается уже при Always-on (lockdown всё равно обязателен для
  защиты смерти процесса) и применяется в `BoxService.startService` перед передачей конфигурации
  любому ядру: обычный старт, reload, sticky/clean-process/package restore.
  Запрошенный fingerprint сохраняется для generation-bound ACK Flutter; эффективный
  конфиг пересобирается отдельно и не сохраняет direct-маршруты.
- В строгом режиме не применяются Smart Route/LAN/direct, route exclusions,
  per-app include/exclude и исключение собственного пакета. Прежние настройки и
  профили не стираются. Чтобы вернуть обычные маршруты, сначала выключить оба
  системных переключателя, проверить состояние с подключённым VPN и нажать
  «Обычные маршруты». Следующий reconnect восстановит сохранённые настройки.
  Автоматического снятия строгого режима при неоднозначном наблюдении нет.
- Конфигурации вне ограниченного контракта одиночного шифрованного outbound
  отклоняются. Произвольные raw/selector/multi-hop JSON не получают небезопасного
  fallback. Ошибки policy не содержат конфигурации и секретов.
- Пользовательский DNS идёт через proxy; DNS bootstrap имени VPN-upstream остаётся
  отдельным разрешённым control-plane исключением. Это не «нулевой DNS вне VPN».
- Собственные HTTP-запросы подписок, обновлений и Geo-IP при сохранённом строгом
  намерении либо VPN/Always-on/lockdown
  или неизвестном состоянии на Android направляются в loopback proxy без `DIRECT`
  fallback. При переходе к VPN/в настройки/в фон direct-операции отменяются; updater
  пересоздаёт отозванный клиент. Оборванную загрузку потребуется повторить.
  Параллельный запрос ждёт завершения записи намерения; ответ старого поколения
  не разрешает прямой запрос после включения строгого режима.
- Состояние ОС читается отдельным кратковременным bind-only query service: это не
  запускает TUN/ядро и позволяет импортировать первую подписку при выключенном VPN.
  Существующий TUN проверяется без bind и без `BIND_AUTO_CREATE` через приватный
  runtime receiver; missing/incomplete reply остаётся неизвестным состоянием.
- Изменение Always-on/lockdown поверх активного runtime обнаруживается нативно
  не позднее следующей проверки (интервал 3 секунды), даже без Flutter UI. До
  завершения пересборки интерфейс не подтверждает строгий TUN. Вход из приложения
  в системные настройки сначала закрывает direct HTTP.
- DNS/TCP-диагностика списка endpoint при строгом/неизвестном состоянии приостановлена.

Система должна уметь отправлять транспортные пакеты VPN через физическую сеть:
`protect(fd)` используется точечно для сокетов ядра. Firewall Android не является
обещанием блокировать абсолютно весь системный/control-plane трафик, tethering,
других пользователей или отдельный work profile. Проверки с самого VPN UID или
через локальный health proxy **не доказывают** блокировку обычных приложений.

## Приёмка на телефоне

Использовать отдельный тестовый UID и только синтетические запросы, без данных
пользователя. Обязателен успешный положительный контроль до fault injection.
Раздельно проверять sing-box/Xray, Wi-Fi/cellular и переходы, недоступный upstream,
падение `:vpn` и всего приложения; закрытие ядра и смерть процесса — разные случаи.
Проверять IPv4, доступный IPv6, HTTPS с проверкой сертификата и UDP/DNS.
Для недоступного семейства/протокола фиксировать пробел покрытия, не PASS.

Сохранять только агрегаты, время, pNNNN и protocol/engine. Не сохранять профили,
endpoint, адреса, SSID/serial, токены, сырые UI XML или пользовательский трафик.
Инъецированные crash отделять от неожиданных crash/ANR. Нерабочие профили с явной
пометкой offline/офлайн не подключать.

## Откат

Отключение системной блокировки снова разрешает прямой интернет — это явное
действие пользователя, не автоматическое лечение. Для программного отката установить
предыдущую APK с тем же сертификатом, не удаляя приложение. Android может запрещать
понижение versionCode; тогда нужна подписанная rollback-сборка с большим кодом.
Не использовать uninstall/clear data: это удалит профили и ключи.

См. [Android VPN](https://developer.android.com/develop/connectivity/vpn) и
[VpnService API](https://developer.android.com/reference/android/net/VpnService).
